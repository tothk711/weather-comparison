## 1. Access — read this before trying to push

### What was attempted

A GitHub fine-grained personal access token was issued for `tothk711/Temperature-Zephyr`
with `Contents: read/write`, stored via `credential.helper store`, and used for
`git clone` (succeeded) and `git push` (failed).

### What is actually happening

This container routes **all** GitHub traffic through a session-level proxy
(`https_proxy=http://127.0.0.1:33449`, `CCR_AGENT_PROXY_ENABLED=1`). The proxy:

- strips any credential the session supplies and injects its own,
- is authenticated as GitHub user **`phasE89`**,
- and enforces a per-session allow-list of repositories.

Evidence:

```
$ git push -u origin chore/lockfile-version-sync
remote: access denied by the git proxy: tothk711/Temperature-Zephyr is not in this
session's authorized repository set, so the proxy will not inject a credential for it.

$ curl -H "Authorization: Bearer <the PAT>" https://api.github.com/repos/tothk711/Temperature-Zephyr
HTTP 403
{"message":"GitHub access to this repository is not enabled for this session.
 Use add_repo to request access..."}

$ curl https://api.github.com/user          # no auth header supplied
HTTP 200  {"login":"phasE89", ...}          # proxy injected its own identity
```

Read access works (clone and `git fetch` both succeed). Only write is refused.

### Consequences

1. **The PAT is useless here and should be revoked.** It was pasted into a chat transcript
   and bought nothing. Revoke at `https://github.com/settings/personal-access-tokens`.
2. **Do not ask for a token again in this environment.** It cannot work by construction.
3. To enable push, the repository must be added to the session's authorized set from the
   Claude desktop app UI. The proxy references an `add_repo` capability, but it is not
   exposed as a tool to the assistant — it is a user-side action.
4. **Check the account identity.** The proxy authenticates as `phasE89`; the repo belongs to
   `tothk711`. If those are different people, `phasE89` needs collaborator write access on
   the repo regardless of what is toggled in the UI.

### Fallback that works today

Patch-based workflow: the assistant works in the container, produces `.patch` files via
`git format-patch`, and the operator applies and pushes locally. Slower per round trip,
but nothing about the overhaul depends on direct write access.

## 4. Findings — prioritized for the overhaul

Line references are against base commit `01e1c4d`. Items marked ✅ were manually
re-verified in the source during this session; the rest come from a full read of
`server.js` and `public/index.html`.

### P0 — correctness, with real trading-data impact

**0.1 · `updated_at` is `TIMESTAMP` without time zone** ✅
`server.js:49` declares `updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP`, written with
`NOW()` (`server.js:396-397`). node-postgres parses `timestamp without time zone` using the
**Node process** local zone. `server.js:1599` then computes
`Date.now() - new Date(cached.updatedAt).getTime() > 3600000`.

If the Postgres session zone and the Node `TZ` differ — a UTC container with
`TZ=Europe/Prague` is the obvious deployment — every row reads 1–2 h off. Failure mode:
the cache always looks stale, so **every `/api/weather` request triggers a fresh upstream
fetch**. That is exactly the rate-limit collapse documented in the v1.4.1 changelog.
Fix direction: `TIMESTAMPTZ`.

**0.2 · Silent memory/DB cache divergence → unbounded refetch loop** ✅
`cacheWeatherData` writes memory first (`server.js:390`), then Postgres, and **swallows the
DB error** (`server.js:401-403`). `getCachedWeather` prefers the DB row and only falls back
to memory when the *read* fails. So after any write failure the DB keeps returning the old
row forever, memory's fresh copy is never consulted, and the 1-hour check refetches on every
request. No metric, no alert — one `console.error`.

**0.3 · `/api/status` is the only route that does not degrade without Postgres** ✅
`server.js:1626-1638` calls `pool.query()` with no `dbReady` guard and no `memWeatherCache`
fallback. Every other route was hardened in v1.2.0; this one was missed. Confirmed 500 in
the mock boot above.

**0.4 · Cached payloads carry baked-in day labels with no midnight invalidation** ✅
`parseWeatherPayload` resolves `today`/`yesterday`/… once at fetch time
(`server.js:198-209`). The TTL is a flat 1 hour with no check that
`data.today.date === getDateString(0)`. A payload written at 23:40 is served as authoritative
until 00:40 — the "Today" line, the Table's Today column and `computeRevisions` all describe
yesterday. Worse: `crossCheckCity` (`server.js:1088`) compares that stale array against
*freshly fetched* model data for the real today, and can flag or overwrite hours as
"suspect"/"corrected". `verifyCache` holds 6 h, so a bad verdict outlives midnight.

**0.5 · No request coalescing on the primary weather path**
`getMedianWeather` has proper in-flight dedup (`medianInFlight`, `server.js:289, 371-385`).
The best_match path has none: `/api/weather/:city` → `fetchAndCache` fires one upstream
request per concurrent caller. The frontend requests 4 Czech cities in parallel for the
Czechia average; a cold start plus the boot fetch plus the cron run can all overlap.

**0.6 · `POST /api/fetch` has no in-flight guard, no auth, no rate limit**
`server.js:1615-1623` runs `fetchAllCities()` — 8 cities × 2 upstream endpoints — on any
unauthenticated POST. Repeated clicks or a trivial curl loop stack overlapping runs.
Concurrent `fetchAndCache` for one city also races the freeze invariant: both read the old
cache, both overlay, last write wins, so **frozen past values can be lost**.

**0.7 · `/api/weather/:city` is the only route with no `try/catch`, and there is no error middleware**
Compare `server.js:1580-1612` with every other handler. Express 4 does not catch rejected
async handlers; there is no `app.use((err,req,res,next)=>…)`, no JSON 404, and no
`process.on('unhandledRejection')`. A throw leaves the request hanging until client timeout,
and Node 20+ terminates the process on unhandled rejection.

**0.8 · History can only address weeks of the current ISO year**
`year` comes from *now* (`server.js:1915`) and `maxWeek = cur.week + 2` (`server.js:1978`).
In January `cur.week === 1`, so the tab offers **three weeks total** and the previous year is
unreachable. For a post-trade review tool that is a functional hole. `setupHistory()` also
runs once at `init()`, so a session open across a week rollover keeps a stale option list.

**0.9 · `express.static('public')` is cwd-relative** (`server.js:1568`) — blank page if the
app is started from anywhere but the repo root.

### P1 — architecture

**1.1 · `server.js` is 14 unrelated subsystems in one file**, with routes split across two
non-contiguous blocks (`1566-1736` and `1966-1988`). There is no fetch/parse/cache/route
layering: `fetchPreparation`, `fetchLive`, `fetchHistory`, `marketBrief`, `crossCheckCity`
and `verifyCity` each re-implement URL building + HTTP + error handling + TTL cache +
stale-fallback inline.

**1.2 · Eight hand-rolled caches, three different entry shapes, none evicts.**
`memWeatherCache:22`, `memMedianCache:288`, `verifyCache:611`, `prepCache:835`,
`crossCheckCache:1073`, `liveCache:1136`, `marketCache:1493`, `historyCache:1910`.
Only `memMedianCache` coalesces. Only prep/live/history/market have stale-on-error —
`crossCheckCache` and `verifyCache` do not. `historyCache` grows unbounded.

**1.3 · `fetchAllCities` reaches forward into caches via a bogus guard** ✅
`server.js:451-459` uses `typeof verifyCache === 'object'` to "guard" a `const` declared at
line 611. `typeof` does **not** protect against TDZ — this works only because the function
first runs after module evaluation. Any refactor that calls it during init throws
`ReferenceError`. It also clears `marketCache`, which a weather refresh does not invalidate.

**1.4 · Copy-pasted logic.** The "cache-miss → fetchAndCache → wrap in `{data}`" dance
appears three times (`656-660`, `1081-1085`, `1708-1712`). Per-model series extraction
exists twice (`extractModelSeries:296` and inline in `fetchHistoryBatch:1895`). Median-of-array
exists three times (`medianOf:1819`, inline in `analyzeCrossCheck:965`, `medianSeries:312`).

**1.5 · Configuration is ~10 scattered module-level literals** with no schema, no validation,
and no startup check that `DATABASE_URL`/`METNO_USER_AGENT` are sane. `MEDIAN_MODELS:287`
and `HISTORY.SOURCES:1761` are two hand-maintained copies of one list — there is a unit test
whose only job is to police the duplication (`tests/server.test.js:103`).

**1.6 · Six Open-Meteo hosts hardcoded as inline template strings** across
`148, 153, 331-332, 616, 634, 846, 1025, 1046, 1203, 1485`. No shared client, no retry or
backoff, no per-host budget — despite two changelog entries about a rate-limit outage.

### P2 — security

**2.1 · Middleware is two lines total** (`server.js:1567-1568`). No `helmet`, no rate
limiting, no auth, no CORS policy, no `x-powered-by` removal, no `trust proxy`. Every route
including `POST /api/fetch` is world-open; the highest-value target is the outbound
amplification in 0.6.

**2.2 · `ssl: { rejectUnauthorized: false }` on the Postgres pool** ✅ (`server.js:15`) —
the DB connection accepts any certificate, so the "encrypted" link is MITM-able. Hardcoded,
not env-gated.

**2.3 · SQL injection: none. Verified clean.** Both dynamic queries are parameterised
(`393-398`, `409-411`); the third is static. No concatenation into SQL anywhere.

**2.4 · Input validation is good on params, absent on structure.** City params are
whitelist-resolved on all 7 routes; `week`/`source`/`country` are validated. But upstream
JSON is trusted with only shallow shape checks before being written to JSONB and served to
browsers, and `express.json()` is mounted with default limits though no route reads a body.

**2.5 · No `.env.example`, no config validation.** `.gitignore` correctly ignores `.env`.
The MET Norway User-Agent falls back to a placeholder that literally says
"set METNO_USER_AGENT" (`server.js:910`) — shipping that violates met.no's ToS and gets the
cross-check source silently banned. This has been an open action item since the v1.2.0
handoff.

**2.6 · Dependency vulnerabilities** (`npm audit`): `body-parser <1.20.6` DoS
(GHSA-v422-hmwv-36x6, via express) and `uuid <11.1.1` bounds (GHSA-w5hq-g745-h8pq, via
`node-cron 3.0.3`). Fixing node-cron needs a major bump.

### P3 — testing

**3.1 · ~26% of exported pure functions have any assertion.** `module.exports`
(`server.js:2016-2027`) exposes 42 names. `tests/server.test.js` has 14 tests asserting
**9 functions**: `isoWeekOf`, `isoWeekDates`, `addDays`, `daysBetween`, `medianOf`,
`buildHistoryTable`, `parseWeatherPayload`, `medianSeries`, `parsePreparation`.

**3.2 · The 26 untested functions include every one that can change a displayed temperature
or emit a trading signal:**

- **`analyzeCrossCheck` (`server.js:948-1001`)** — the consensus-override logic that silently
  replaces displayed values with the median of other models. **Highest-risk function in the
  codebase. Zero tests.** If one thing gets a test suite first, it is this.
- `freezePastDays` / `computePastAvg` (`84-108`, `67-78`) — the write-once history invariant
  the whole post-trade-review use case rests on. Zero tests.
- `parseMarketCity`, `buildMarketBrief`, `windPowerAt`, `windPowerIndex`, `solarIndex`,
  `degreeDays`, `signalDir` (`1273-1479`) — the entire market brief, ~200 lines of thresholds
  and weighted averages. Zero tests.
- `computeRevisions` / `reviseDay` (`1537-1564`) — the forecast-revision signal. Zero tests.
- `runDataChecks` (`502-608`, 5 check families), `parseLive`, `seriesToDays`,
  `localHourIndex`, `nowInTz`, `haversineKm`, `buildNotes`, `classify*`, `describeWeather`,
  `liveDir`, `modelLabel`.

**3.3 · Zero integration/route tests.** All 14 handlers, the cache layer, `initDB`, the
freeze-on-refetch integration, the DB-absent path and `start()` are unexercised.
`tests/mock-fetch.js` is capable of driving all of this and is not wired to anything.

**3.4 · No coverage tooling. No timezone test** — `getDateString`'s DST/midnight anchoring
is documented at length (`server.js:115-136`) and asserted nowhere.

### P4 — tooling

**4.1 · `package.json` has no `devDependencies` at all.** Verified absent: `.eslintrc*`,
`.prettierrc*`, `.editorconfig`, `Dockerfile`, `.dockerignore`, `.github/` (no CI),
`tsconfig.json`, `.env.example`, `Procfile`, `.nvmrc`. Nothing prevents the next 2000-line
file.

**4.2 · Dependency freshness** ✅: `express 4.22.2` → 5.2.1 available (4.x is *why* async
route errors are swallowed, see 0.7); `node-cron 3.0.3` → 4.6.0; `pg 8.22.0` → 8.23.0.
`engines.node >= 20` with no `.nvmrc` or CI matrix pinning it.

**4.3 · No operational surface.** No `/health` or `/ready`, no structured logging (57 raw
`console.*` calls), no cache-hit or upstream-failure metrics — which is why 0.1 and 0.2 could
run for months undetected. `cron.schedule('0 */6 * * *')` (`server.js:1996`) has **no
`timezone` option**, so the refresh follows the container's zone while all data math is
pinned to `Europe/Prague`.

### P5 — frontend

**5.1 · 2,499 lines in one file, no build step**: CSS `11-684`, markup `686-891`,
JS `891-2497` (1,606 lines). No modules, bundler, minification, source maps, tests or lint.

**5.2 · Two CDN `<script>` tags are hard runtime dependencies with no SRI and no fallback**
(`public/index.html:9-10`, Chart.js 4.5.1 + annotation plugin 3.1.0 from jsDelivr). If
jsDelivr is blocked — common on trading-desk networks — the dashboard is blank. No
`integrity` attribute on either.

**5.3 · Global mutable state, no container.** `leftChart`, `rightChart`, `leftCity`,
`rightCity`, `graphSource`, `cityDataCache` (`898-907`) plus the table/history state around
`1660-1665`. **`cityDataCache` has no TTL** — it is cleared only by the manual refresh button,
so a tab left open all day serves morning data indefinitely while the header still reads
"Last updated".

**5.4 · 13 inline `onclick=` handlers** (`694, 698-704, 721-722, 771-772, 823`) force every
handler into global scope, blocking any module or CSP migration.

**5.5 · Business logic in the browser.** `calculateCzechiaAverage` (`989-1023`) reimplements
per-hour averaging that exists server-side, against a hardcoded city list that duplicates
`MARKET.COUNTRIES.CZ` — **with different semantics** (unweighted mean vs population-weighted).
The client also reimplements the server's ISO-week math verbatim (`1666-1688` vs
`server.js:1794-1816`), with a comment admitting they are "kept in lockstep" by hand.

**5.6 · Duplicated render logic.** `renderTable` (`1426-1477`) and `renderHistory`
(`1748-1786`) are near-identical heat-grid builders. Every left/right chart path is a
`side === 'left' ? … : …` ternary rather than an instance. `renderChart` is a 250-line
function (`2247-2496`) with 8 hand-written dataset literals differing only in colour and dash.

**5.7 · 37 `innerHTML` assignments, no escaping helper anywhere.** `public/index.html:1738`
writes `data.error` from the API response straight into `innerHTML`. Not currently
exploitable — all data originates from Open-Meteo and this server — but it is a codebase-wide
pattern with zero defence that forecloses a CSP.

## 5. Suggested sequencing for the overhaul

Not a plan — a proposed order of operations, to be agreed with Vit before any code moves.

1. **Resolve push access** (section 1). Everything else is friction until this is done.
2. **Characterization tests before refactoring.** `analyzeCrossCheck`, `freezePastDays`,
   `computeRevisions` and the market builders first — these encode judgement that must not
   change silently during a restructure. Wire `tests/mock-fetch.js` into `npm test` as the
   route-level harness that already exists but is unused.
3. **Add the tooling floor**: ESLint + Prettier, `.env.example`, `.nvmrc`, a GitHub Actions
   workflow running `npm test`. Cheap, and it stops the codebase drifting further while the
   overhaul is in flight.
4. **Fix the P0 correctness bugs** — they are small, independent, and each is a live
   production risk. 0.1, 0.2, 0.3 and 0.4 are the ones that can quietly corrupt what the desk
   sees.
5. **Then** consider structural work: extract an Open-Meteo client, unify the eight caches
   behind one abstraction, split `server.js` by subsystem, and decide the frontend's future
   (module split vs a real framework).

Deliberately unranked: whether to migrate to TypeScript, whether to move to Express 5, and
whether the frontend gets a build step. Those are direction decisions, not defects.
